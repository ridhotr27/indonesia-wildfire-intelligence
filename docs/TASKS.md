## 1. Status and approval policy

### Ticket lifecycle

`BACKLOG → READY → IN_PROGRESS → IN_REVIEW → DONE`

`BLOCKED` may be entered from any non-`DONE` state and returns to the appropriate state only after the blocker is resolved.

- **BACKLOG:** Defined, but not yet eligible to start because it is sequenced behind unfinished work or not selected for execution.
- **READY:** All start dependencies are satisfied, scope and owner are clear, and the ticket may be claimed.
- **IN_PROGRESS:** One named agent/session has claimed the ticket and is actively changing its owned files.
- **IN_REVIEW:** The implementation/evidence and required verification are complete enough for review; this is technical completion, not approval.
- **DONE:** Acceptance criteria and required verification are evidenced, deliverables exist, and the Tech Lead has recorded approval in this backlog or an explicitly linked review record.
- **BLOCKED:** Work cannot safely proceed because an approval, external fact, contract, credential, or other named prerequisite is missing. The blocker and unblock condition must be recorded.

Status transitions are forward-only unless review finds a defect or scope change. An agent may move a ticket through `READY`, `IN_PROGRESS`, and `IN_REVIEW`, but only the Tech Lead may move it to `DONE`, approve a gate, change a shared contract, or waive a dependency. Passing tests alone never means `DONE`. No status may cite a test that was not actually run.

### Gate lifecycle and dependency rules

Gates are approval decisions, not implementation tickets:

| Gate | Status | Requires | Approval record needed |
|---|---|---|---|
| G0 — product scope | **APPROVED — 2026-10-22** | P01 `DONE`; PRD approved for v1.0 implementation | Tech Lead approval recorded in this backlog and `docs/PRD.md` |

Dependencies are start dependencies unless a ticket explicitly separates an independent mock/scaffold phase. A dependent ticket normally cannot become `READY` until ticket dependencies are `DONE` and gate dependencies are approved. Existing speculative foundations do not satisfy or bypass D04, A01, or G2. Any exception requires a recorded Tech Lead decision.

### Technical completion versus approval

Each review must record two distinct facts:

1. **Implementation/evidence state:** files delivered and exact checks run, including failures, warnings, and limitations.
2. **Approval state:** Tech Lead acceptance, requested changes, or unresolved decision.

`IN_REVIEW` means the first may be complete while the second is pending. `DONE` requires both. Before the explicit 2026-10-22 Tech Lead approval, D03, B01, and F01–F05 demonstrated this distinction; their implementation evidence remains unchanged by approval.

## 2. Ownership, worktrees, shared files, and review

- One ticket has one accountable owner role and one active agent/session at a time. Joint-owner tickets must name the handoff owner when claimed; joint ownership does not authorize concurrent edits to the same files.
- DE owns `data/`; BE owns `backend/`; FE owns `frontend/`. Credentials and ClickHouse write access remain DE-only; BE serving access is read-only; FE never accesses ClickHouse, Qdrant, NASA APIs, or LLM credentials directly.
- Lead DevOps Engineer prepares infrastructure, CI/CD, deployment, backups, monitoring, and rollback evidence for Tech Lead review. Tech Lead remains accountable for R01, shared-file decisions, production authorization, and release approval; this role does not inherit DE/BE/FE application or data-write ownership.
- Each implementation agent uses a separate branch and Git worktree (for example `agent/data-engineer`, `agent/backend`, `agent/frontend`, `agent/lead-devops-engineer`). Before work begins, record the ticket ID in the branch/PR title and confirm the worktree is clean enough to distinguish pre-existing changes.
- `docs/`, `infrastructure/`, root configuration, schemas, fixtures used across roles, and public contracts are shared. Only one coordinated editor may modify a shared file at a time. Shared changes require a dedicated review; agents must not copy divergent versions between worktrees.
- Contract proposals are versioned and immutable once approved. Breaking changes require a new version and coordinated DE/BE/FE review. Draft/mock implementations must remain visibly labeled and must not be represented as real NASA analytics.
- A claim must include dependencies checked, intended files, and verification plan. A handoff/review must include changed files, exact commands/results, limitations, security/data claims, and next dependency.
- Only the Tech Lead approves gates, shared contracts, architectural exceptions, and `DONE`. Review approval must be explicit; silence, a green test suite, implementation existence, or mergeability is not approval.
- Never invent data access, boundary permission, observations, metrics, downloads, or test results. Hotspots remain satellite detections, not confirmed fires or burned hectares.
