# Wildfire private deployment operations

This procedure uses one Wildfire Compose project on the existing VPS. The owner authorized a public portfolio demo on 2026-11-25 despite Q01's recorded no-go recommendation. The earlier private-only instructions below describe the original experiment; the observed public-route state is recorded next. Q01's failed and unmeasured results remain unchanged, and R01 is not marked `DONE`.

## Owner-authorized public demo state — 2026-11-25

The shared Caddy container was attached to `wildfire_edge`, and the validated site block in `infrastructure/caddy/shared-edge-wildfire.Caddyfile` was appended to `/opt/shared-edge/deploy/Caddyfile`. Its prior content is backed up at `/opt/shared-edge/deploy/Caddyfile.r01-prewildfire`. Caddy v2.11.9 reloaded the file with `SIGUSR1` without restarting the portfolio; the portfolio remained HTTPS 200. The protected Wildfire environment was backed up at `/opt/indonesia-wildfire-intelligence/.env.production.r01-prepublic` before setting the browser API origin to `https://wildfire.ridhotrivo.com/api/v1` and the matching CORS origin. Wildfire frontend/backend/ClickHouse/Ollama remained healthy and private on their Docker networks.

Public HTTPS was **not verified** at this point: NeoDNS returned NXDOMAIN for `wildfire.ridhotrivo.com`, and Let's Encrypt could not issue its certificate. The DNS owner must create A record `wildfire` → `139.190.108.107`; no AAAA record is needed. After DNS resolves, verify HTTPS dashboard, API, map, and chatbot journeys, headers, portfolio health, host memory/swap, and Caddy certificate issuance before reporting a working public URL. To undo this route, copy the Caddy backup content over the active bind-mounted Caddyfile, validate it, send `SIGUSR1` to shared Caddy, and disconnect only shared Caddy from `wildfire_edge`. To restore private browser settings, copy the protected prepublic environment backup over `.env.production` and recreate only Wildfire frontend/backend. Do not delete persistent volumes.

### Public HTTPS recovery — 2026-11-26

NeoDNS A resolution reached both the VPS and shared Caddy, but Caddy's prior ACME attempt had failed while DNS was NXDOMAIN. The validated Caddyfile was gracefully reloaded with `SIGUSR1` to retry issuance; Let's Encrypt HTTP-01 succeeded and a trusted certificate for `wildfire.ridhotrivo.com` was issued (expires 2027-02-24 UTC). External HTTPS checks returned 200 for the dashboard, runtime configuration, API health, metadata, and a 261-feature 2023 map response. One public NASA RAG chat returned 200 with two citations in 60.19 seconds. The portfolio remained HTTPS 200; ClickHouse and Ollama still had no published host ports. After that request, host RAM available was 2,256 MiB, swap used was 174 MiB with no observed ongoing swap-in/out, and Ollama reported zero OOM kills. Ollama's cgroup reached its 1 GiB limit and recorded 205 max-limit events, so this public demo remains resource-sensitive; retain the existing stop/rollback triggers and do not reinterpret these smoke results as Q01 metric passes.

## Experimental low-memory profile

`docker-compose.low-memory.yml` is an opt-in overlay. The original `docker-compose.prod.yml` remains the rollback baseline. It sets container ceilings of 1024 MiB ClickHouse, 384 MiB backend, 256 MiB frontend, and 1024 MiB Ollama (1664 MiB without Ollama; 2688 MiB with it). The ClickHouse config also bounds server/query memory, caches, query threads, concurrency, and external sort/group-by spill. Backend remains one worker with four concurrent requests; Next.js uses a 160 MiB V8 heap ceiling. Ollama remains an optional profile with one loaded model, one parallel request, 2048 context, and immediate idle unload. These settings are experimental limits, not observed usage or proof that startup and queries succeed.

Validate syntax locally without revealing resolved secrets:

```bash
docker compose --env-file .env.example -f docker-compose.prod.yml -f docker-compose.low-memory.yml config --quiet
docker compose --env-file .env.example -f docker-compose.prod.yml -f docker-compose.low-memory.yml --profile local-llm config --quiet
```

After separate approval for a **private** host experiment, use the host's protected `.env.production` and the same Compose file order. Start ClickHouse, backend, frontend, then optional Ollama one service at a time with `docker compose --env-file .env.production -f docker-compose.prod.yml -f docker-compose.low-memory.yml up -d <service>`. Before and after each start and representative approved analytics/map/RAG request, record `docker stats --no-stream`, `free -h`, `swapon --show`, `docker compose --env-file .env.production -f docker-compose.prod.yml -f docker-compose.low-memory.yml ps`, container `memory.current`/`memory.peak`/`memory.events` from the cgroup, CPU, latency, and portfolio health. Inspect ClickHouse effective settings with `SELECT name, value FROM system.settings WHERE name IN ('max_memory_usage','max_threads','max_insert_threads','max_bytes_before_external_group_by','max_bytes_before_external_sort')` and confirm query parity with the approved DE reference results. Test the maximum bounded map response and representative NASA RAG questions. An Ollama test additionally requires the existing approved model and BE-approved embedding/index profile; do not pull a model or enable `local_grounded` solely to exercise this overlay. Stop the experiment at OOM, sustained swap activity, failed parity, or portfolio degradation.

Rollback the experiment by recreating Wildfire services with **only** `docker-compose.prod.yml` and the prior approved image SHA; do not delete named volumes or run `down --volumes`. DE owns any data-release rollback. Keep public routing disabled throughout the experiment.

## Prerequisites

The host has an operator-managed source archive at `/opt/indonesia-wildfire-intelligence`, a mode-0600 `.env.production`, private Compose networks, and persistent volumes. Keep deployment credentials and `.env.production` out of GitHub and logs. The CD job verifies exact checksums of the host's production and low-memory Compose files and the image overlay before pulling; this fails closed if operator-managed infrastructure drifts. GitHub CI builds and publishes linux/amd64 images only after backend, data, frontend, and Compose checks pass on `main`. PRs build without publishing.

The `production` GitHub environment must have required reviewers and two environment secrets: `VPS_SSH_PRIVATE_KEY` (the restricted deploy identity) and `VPS_SSH_KNOWN_HOSTS` (the previously verified host-key line for `139.190.108.107`). Restrict the environment to protected `main`; branch protection must require the existing CI checks and review. Do not use `ssh-keyscan` as a trust source in the workflow. The runner uses its scoped `GITHUB_TOKEN` to pull GHCR images through a temporary Docker config; the host does not retain that token.

After successful main CI, or an approved `workflow_dispatch` on main, the serialized CD job passes the published backend and frontend image digests to `infrastructure/scripts/deploy-release.sh` on the host. The script checks host Compose checksums, protected environment mode, baseline health, the verified 253,388-row 2023 dataset, portfolio availability, RAM and disk headroom. It pulls digest-pinned linux/amd64 images and recreates only backend and frontend, without dependencies, builds, or volume removal. It checks both container health, unchanged ClickHouse/Ollama/Caddy identities and dataset count, and public Wildfire and portfolio endpoints. On failure after application mutation it restores the previously running backend/frontend image references. Inspect the health checks and perform operator recovery if rollback also fails. The current successful image refs are stored in host-local `.last-good-image-refs`. No migration, ingestion, LLM, DNS, Caddy or volume operation is part of CD. Never use `docker compose down --volumes`.

Before each dispatch, verify backup freshness and a restore test, image digests, free memory/disk, current portfolio status, ClickHouse release and grants, and schema compatibility. Do not run destructive migrations in the deploy job. After health succeeds, run private metadata, analytics, NASA citation, and frontend browser smokes, plus portfolio checks. A container health pass alone is insufficient for release acceptance. If any check fails, restore the prior SHA and use the DE append-only data rollback procedure if a separately approved data release changed.

Monitor `free -h`, `swapon --show`, `df -h`, `df -i`, `docker stats --no-stream`, `docker compose ps`, ClickHouse errors and persistent log growth, API 5xx/p95, index compatibility, Caddy certificate expiry, and portfolio availability. Set a low-cost external HTTPS probe and record alert recipient and response before public release. Off-host encrypted backups must include ClickHouse data/metadata, RAG index and manifest, deployed SHA/digests, and secrets in a separate restricted store. Test restoration into a new empty volume; never overwrite the only production copy.
